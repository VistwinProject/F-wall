## 1. 規劃與目標

F 區是一個「把看不見的智慧家庭串聯講給人看」的實體互動裝置。
它的核心不是螢幕，是桌面上那九張卡。

### 1.1 展區敘事

觀眾拿起前方的實體家電模型，放上桌面投影的 NFC 感應區。
**三個畫面在同一瞬間反應**：

- **桌面** 亮起那台的即時數據面板
- **牆面** 亮起牆上對應展品的框，並跑出一道走線光束射向中央 AI 核心
- **iPad** 上的知識圖譜長出一條新的連線

九台全部放上時，三端一起收束成「全屋家電已串聯至 AI 大腦」。

整個裝置**只有一個互動動作**（放卡 / 拿卡），所有視覺複雜度都用來服務這一個動作的回饋。
這是 1.0 最正確的決定，2.0 必須守住。

### 1.2 三端角色

| 畫面 | Repo | Port | 角色 | 資料方向 |
| --- | --- | --- | --- | --- |
| **桌面投影** | `F-table/web` | 5173 | 感應區本體 ＋ 家電數據面板 | 收 WS、可送 session 控制 |
| **牆面投影** | `F-wall` | 5174 | 全屋走線與家電狀態的大畫面 | **只收不送** |
| **iPad** | `F-Ipad` | 5175 | 觀眾手上的知識圖譜 / 操作端 | 收 WS、送 session 控制 |
| **WS server** | `F-table/server` | 8787 | 權威狀態，接 ACR122U ×9 | 廣播給三端 |

### 1.3 九台家電（id 已凍結）

> 這九個 id 字串橫跨三端 ＋ server 的 `uid-map.json` ＋ 已經貼在實體卡片上的 UID 對應。
> 2.0 可以重寫每一行程式碼，但**不准改這九個字串**——改了現場的實體卡片就要重新登記。

| `dehum` | 除濕機 | DH-01 | 目前濕度 72% | 待登記 |
| `purifier` | 空氣清淨機 | AP-06 | PM2.5 8 µg/m³ | 待登記 |

### 1.4 六條設計原則

這六條不是風格偏好，每一條背後都有一個現場的物理限制或觀眾條件。2.0 全部沿用。

| 原則 | 為什麼 |
| --- | --- |
| **投影機的黑 ＝ 不出光** | 牆上十一個框是*實體展品的預留位*。那幾塊一律 `#000`，不是配色選擇——不純黑的話投影光會打亮真的家電模型。也因此核心框裡**不放任何文字**。 |
| **文字一律白色** | 線 / 邊框 / 光暈染淡藍，字不染。展場觀眾偏年長，藍字在投影上更難讀。 |
| **canvas 只負責「光」** | 要銳利的東西（文字、毛玻璃、實心白點、黑塊）一律留在 DOM / SVG。光進 WebGL 過 bloom；銳利的東西進 canvas 只會被 bloom 糊掉。 |
| **只有三種循環動畫** | 走線彗星、底光呼吸、進出場淡入淡出。*沒有第四種*。1.0 早期的旋轉刻度、掃描弧、放射線、同心環全部移除了——那些不承載任何資訊。 |
| **彗星不呼吸** | 它是資料封包。跟著明暗會讀成「訊號不穩」。底光呼吸、彗星恆亮，這個分工要守住。 |
| **節奏放慢給年長觀眾** | 桌面面板輪播 8 秒（不是 5 秒）、進出場 0.28s、歡迎頁淡出 600ms 三端綁在一起。 |

### 1.5 1.0 目前的已知限制

這些是 2.0 的實際待辦，不是抱怨清單。

- **毛玻璃無法進 WebGL。** `backdrop-filter` 是 CSS box 屬性，SVG 與 WebGL 都沒有等價物
  （SVG 1.1 規劃過的 `BackgroundImage` 濾鏡輸入沒有任何瀏覽器實作過）。
  三端的玻璃靠 token 統一，不是靠同一套繪圖。牆面自己也是用 `foreignObject` 包一個 div 來做。
- **共用程式碼是「複製」而不是套件。** `glow/` 與 `shared/` 由 `sync-tokens.mjs` 從 F-wall 複製到另外兩端。
  好處是每個資料夾自帶完整程式碼、現場複製一個夾就能跑；代價是直接改複製品會被下次同步蓋掉。
- **iPad 的線粗刻意不跟 `SHARED` 走**（0.009 / 0.011 對 0.013542）。
  圖譜線要比牆面格線細很多才好看，代價是改 `SHARED` 不會連動 iPad。
- **牆面面板已改成絕對座標。** `panels.js` 的 `PANEL_LAYOUT` 取代了原本的自動避讓，
  所以黑塊座標一改，面板*不會*跟著跑，要開編輯模式重對一次。
- **`--sim` 不能與真硬體同時用。** 它會把九個 slot 標成虛擬讀卡機在線，真讀卡機插上來會被跳過。
- **F-table 的 git 歷史有一顆 54.6 MB 的 `.ply`**（3DGS 時期留下的），功能已移除但歷史清不掉。
  2.0 是重建新 repo 的好機會。
- **iPad 直向**會把左右卡片擠在一起壓到平面圖。展場橫放，1.0 不處理。

## 2. 系統運作流程

權威狀態只有一份，在 server。三端都是「收到廣播才改畫面」，沒有任何一端在本地搶先切換。

### 2.1 訊號拓樸

```
                  ACR122U × 9
                 （實體 NFC 讀卡機）
                        │
                        ▼
          ┌─────────────────────────────┐
     ┌───▶│  F-table/server : 8787      │◀───┐
     │    │  權威狀態 · broadcast        │    │
     │    └─────────────────────────────┘    │
     │                  │                    │
     │      ┌───────────┼───────────┐        │
     │      ▼           ▼           ▼        │
     │  ┌───────┐  ┌────────┐  ┌────────┐    │
     └──┤ 桌面   │  │ 牆面    │  │ iPad   ├────┘
        │ 5173  │  │ 5174   │  │ 5175   │
        │收＋送  │  │只收不送 │  │收＋送   │
        └───────┘  └────────┘  └────────┘

實線（│▼）＝ 卡片事件廣播
虛線（└──┘）＝ session 控制：送出後由 server 轉發回全部人（含送出者）
```

### 2.2 訊息協議（六種）

| type | 攜帶欄位 | 意義 | 誰處理 |
| --- | --- | --- | --- |
| `reader-connected` | `slot_index`, `reader` | 讀卡機上線、尚無卡 | 桌面、iPad（牆面略過） |
| `tag-present` | `slot_index`, `uid`, `known`, `data{ id, label, description }` | 卡片放上 | 三端 |
| `tag-remove` | **只有 `slot_index`** | 卡片拿走 | 三端 |
| `reader-disconnected` | `slot_index` | 讀卡機離線 | 三端 |
| `session-start` | — | 離開歡迎頁 | 三端 |
| `session-end` | — | 回到歡迎頁 | 三端 |

> **踩過的坑 — `tag-remove` 不帶 id**
> 所以每一端都必須自己記一份 `slot_index → id` 的對應
> （最後一次 `tag-present` 在該 slot 看到的 `data.id`），拿走時才知道要熄滅哪一台。
> 三端目前都各自實作了這個記帳——**2.0 應該把它抽成共用的 hook，不要再寫三份。**

> **踩過的坑 — session 控制不可以本地先切**
> 送出 `session-start` 之後要等 server 廣播回來才切畫面。
> 直接本地切的話送出的那一端會早其他兩端 1 個 RTT，三端不會同時切。
> WS 斷線時才走本地 fallback（同樣的 600ms 淡出時序）。

### 2.3 路由原則：以 id 而非 slot

三端一律以 **家電 id 路由**（`data.id`），不是以 slot 位置路由——
卡片放在哪一個感應區都會亮對的家電。

slot 只用來做兩件事：桌面畫面上九個圈的定位，以及上面那個熄燈記帳。

server 端有一張 `reader-map.json` 把讀卡機名稱釘到畫面編號（1–9）：

```json
{
  "ACS ACR122U PICC Interface 00": 1,
  "ACS ACR122U PICC Interface 01": 2
}
```

沒有這張表時 slot 依偵測順序發號碼，也就是 **USB 插入順序會決定桌上哪一台對到畫面哪一個圈**。
現場佈線一定要建這張表。檔案不存在時 server 會退回自動配號並在終端機提示，不會卡住。

### 2.4 Session 狀態機

```
welcome ──(任一端送 session-start)──▶ live
   ▲                                     │
   └────────(任一端送 session-end)────────┘
```

- **歡迎頁**：純黑底 ＋「歡 迎 來 到」＋「AI 大腦控制塔」＋ 指示文字，600ms 淡出（**三端的時長綁在一起**）
- **重置**：iPad 右下角有給工作人員的「↺ 重置」鈕
- **牆面**：沒有歡迎頁——它一直顯示待機的背景框架

歡迎頁文案（三端一致）：

```
歡 迎 來 到
「AI 大腦控制塔」
請拿取前方設備裝置，放置相對的感應範圍，
開始將居家設備連結到 AI 大腦！
```

（iPad 多一行「點擊任意位置開始」；桌面拿掉了，因為投影面不可觸控。）

### 2.5 三個執行模式

| 模式 | 怎麼進 | 行為 |
| --- | --- | --- |
| **現場** | `http://` ＋ 真 server | 接 ACR122U。`protocol === 'http:'` 所以不會誤入展示模式。 |
| **展示** | `https://` 自動<br>或 `?demo` | `DemoSocket` 頂替真 server：介面與欄位形狀**逐欄位相同**，接收端一行都不用改。 |
| **鍵盤模擬** | server 帶 `--sim` | `1`–`9` 放上／拿走、`a` 全放、`0` 全拿。 |

**展示模式的自動編排**：

```js
const STEP_MS  = 2600   // 每放一台的間隔
const HOLD_MS  = 5000   // 九台全亮後停留
const CLEAR_MS = 420    // 收掉時每台的間隔
const OPEN_MS  = 260    // 「連上」的延遲，讓 UI 有一瞬間的 connecting 狀態
```

按任何鍵就停掉自動編排（不然自動流程會跟手動搶著改狀態）。

**鍵盤模擬的關鍵**：前端**不自己模擬**，只把按鍵送給 server 由它廣播——
這樣三端才會一起亮，那正是要驗證的東西。各端自己模擬只會讓那一端亮，看不出同步。
開關**只有一個**：server 要帶 `--sim`。沒帶時完全忽略並在終端機提示一次
（前端不再另外要求網址帶 `?sim`——兩道關卡只會讓人按了沒反應又不知道為什麼）。

> **踩過的坑 — 為什麼 https 要自動進展示模式**
> 真實資料來自 `ws://<host>:8787`，而瀏覽器**硬性禁止**從 https 頁面連 `ws://`
> （mixed content，無法用設定放行）。也就是說 https 之下真的那條路一定連不上，
> 而且連「連不上再重試」都不會發生——不自動切的話使用者看到的是一個永遠在重連的離線畫面，
> 而且沒有任何提示說要加 `?demo`。
>
> 判斷順序：`?live` 強制真連線 > `?demo` 強制展示 > `protocol === 'https:'` 自動展示。

> **踩過的坑 — `DemoSocket` 的自動編排用遞迴 `setTimeout`**
> 不要用 `setInterval`。分頁被切到背景時 interval 會累積成一串補跑的 tick，
> 回到前景會看到九台瞬間全亮。

### 2.6 現場逃生開關（牆面）

| 參數 | 作用 | 什麼時候用 |
| --- | --- | --- |
| `?all` | 強制九台全 active | 驗證面板／連線排版不打架 |
| `?fps` | 左下角顯示幀率 / 最長幀 / 掉幀數 | 實機效能驗證 |
| `?noglass` | 毛玻璃換成不透明底板 `#0b0d11` | 投影機上毛玻璃掉幀 |
| `?nofx` | 完全不掛 WebGL 發光層 | GPU 有問題 |
| `?edit` | 面板版面編輯器（平常按 `e`） | 現場對位 |
| `?glowdbg` | 保留繪圖緩衝，可 `readPixels` 量真實輸出 | 調光時「量」而不是「猜」 |

iPad 另有 `?ws=host` 手動指定 WS server 位址（預設用 `location.hostname`）。

三端都用鍵盤 `e` 開啟版面編輯模式。展場的投影機沒接鍵盤、iPad 沒有實體鍵盤，
所以按鍵開啟是安全的。
**有覆寫值時畫面角落會一直顯示「已套用編輯值」**——
那是唯一會讓人發現「現在畫面不是程式碼裡那一版」的線索，2.0 一定要保留。

## 3. 視覺系統核心

三個畫面的「淡藍發光線段 ＋ 毛玻璃面板 ＋ 走線彗星」是**同一套程式碼**，
不是各自調到看起來很像。這是 1.0 最重要的架構決定。

### 3.1 單一來源與同步

| 內容 | 位置 | 散佈方式 |
| --- | --- | --- |
| 顏色、毛玻璃、彗星參數 | `F-wall/src/config/fx.js` → `SHARED` | 產生三端 CSS 的 `GLOW-TOKENS` 區塊 |
| WebGL 發光層（shader / bloom / 彗星） | `F-wall/src/glow/` | 整個資料夾複製到另兩端 |
| 鍵盤模擬、DemoSocket | `F-wall/src/shared/` | 同上 |
| 換算後的執行期參數 | `glow/params.js` | **自動產生**，不要手改 |

```bash
# 改完 SHARED 之後
cd F-wall && node sync-tokens.mjs

# CI 檢查有沒有飄掉（飄掉就 exit 1）
node sync-tokens.mjs --check
```

腳本預期三個專案是**並排的同層資料夾**。只 clone 了 F-wall 的話它會直接報錯說明，
不會安靜地建出一堆空資料夾。

### 3.2 色票

| Token | 值 | 用途 |
| --- | --- | --- |
| `--glow` | `#A0D8FF` | 框架格線、家電框外圈、節點外圈 |
| `--glow-core` | `#DCEFFF` | 亮芯。牆面靠 bloom 過曝自然產生；iPad / 桌面沒有那麼強的 bloom，用這個近白色頂上 |
| `--glow-beam` | `#7FE3FF` | 走線光束身部（彗星 body） |
| `--glow-deep` | `#1B4FA8` | 彗星尾端 |
| `--glow-head` | `#FFFFFF` | 彗星頭。**超過 1.0 就是 bloom 的來源** |
| 底色 | `#16181D` | 三端一致。WebGL canvas 用同一個值清除畫面 |
| 十一個框 | `#000000` | 純黑，非配色選擇（見原則一） |

底色三端必須一致——不一致的話 letterbox 邊界（非 16:9 投影時）會出現一條色差接縫。

**狀態語意刻意走無彩**：`ok` / `warn` / `err` 三階都是不同不透明度的白，
語意由文字（「即將到期」/「離線」）與「圓點實心 vs 空心」承擔。
想開回功能色的話 1.0 在 `theme.js` 留了註解好的兩行（`warn: '#f59e0b'` / `err: '#f43f5e'`）。

其他 token：

```js
// 線 / 邊框（分層就靠這三階）
line:       'rgba(255,255,255,0.10)'  // 極細灰線、hairline、idle 走線
lineStrong: 'rgba(255,255,255,0.22)'  // 面板外框、分隔線
lineActive: 'rgba(255,255,255,0.85)'  // active 白高光

// 文字
text:         'rgba(255,255,255,0.95)'
text2:        'rgba(255,255,255,0.62)'
text3:        'rgba(255,255,255,0.38)'
textOnGlass:  'rgba(255,255,255,0.55)'  // ← 見下

RADIUS = { sm: 6, md: 12 }   // sm = 黑塊與家電框，md = 毛玻璃面板
MOTION = { dur: 0.28, ease: [0.16, 1, 0.3, 1] }

FONT = '-apple-system, BlinkMacSystemFont, "Segoe UI", Helvetica, Arial,
        "Chiron Hei HK", "PingFang TC", "Microsoft JhengHei", sans-serif'
```

`textOnGlass` 的由來：面板改成半透明之後底板亮度從 ~10 升到 ~49，
`text3`(0.38) 的對比只剩 3.25:1（低於 AA）；0.55 拉回 5.10:1。
這是「把字提亮」而不是「把玻璃調濁」——玻璃感不用退讓。
只有面板內的設備代碼與資料列左標籤用它。

字體刻意**拿掉等寬 HUD 字**（那是舊科幻感的主要來源），數字改用系統字 ＋ `tabular-nums` 對齊。

### 3.3 分層原則（三端一致）

```
  DOM / SVG    ◀── 文字、毛玻璃面板、實心白點、黑塊
  ─────────────
  WebGL canvas ◀── 發光線、光暈、走線彗星（過 UnrealBloomPass）
  ─────────────
  背景          ◀── 牆面：純色 ／ iPad：俯視渲染圖 ／ 桌面：流動漸層
```

各端實際 z-index：

| 牆面 | iPad | 桌面 |
| --- | --- | --- |
| `1` SVG：黑塊＋面板＋文字 | `7` 家電卡片 | `3` 連線 SVG（fallback 細線） |
| `0` WebGL canvas（含背景框架） | `6` 中樞環＋標籤 | `2` NFC slot 圈 |
| | `5` 節點白點 | `1` WebGL 發光層＋中樞 |
| | `2` leader 線 SVG | `0` 流動漸層背景 |
| | `1` WebGL 發光層 | |
| | `0` TOP.png 俯視渲染圖 | |

> **踩過的坑 — 分層順序**
> **牆面的 SVG 必須疊在 canvas 之上。** bloom 一定會往黑塊裡面溢，
> 靠上層 SVG 的 `fill="#000"` 蓋掉。
>
> 牆面 canvas 是**不透明**的（框架也在裡面，底下不需要透出任何東西）；
> iPad / 桌面是**透明**的（底下要透出平面圖與漸層）。這個差別由 shader 的 `uAlphaLuma` 控制。
>
> **iPad 踩過的坑**：背景原本疊在發光層*之上*（那時是幾乎透明的示意 SVG，所以沒差）。
> 換成不透明的渲染圖之後整層光被蓋掉。現在順序是照片(0) → 發光層(1)。

### 3.4 WebGL 發光層架構

五個檔案，職責切得很乾淨。2.0 建議原封不動搬過去，然後把它打包成真正的套件。

| 檔案 | 職責 | 要注意的 |
| --- | --- | --- |
| `glow/shaders.js` | GLSL：`LINE_*`（發光線）＋ `BEAM_*`（彗星） | 「牆面的光長什麼樣子」的**唯一定義**。牆面的 `webgl/` 也 import 這裡 |
| `glow/ribbon.js` | 沿一串點鋪三角帶，產出 `aSide`（橫剖面 −1→0→+1）與 `aT`（等弧長 0..1） | `aT` 必須是**等弧長**，用「第幾個點」會讓彗星忽快忽慢 |
| `glow/stage.js` | renderer / 正交相機 / EffectComposer ＋ UnrealBloomPass | 緩衝固定**面積**約 1.6 MP，不跟視窗跑 |
| `glow/scene.js` | 把折線陣列變成 mesh：`createGlowLines` / `createGlowBeams` | 每條線畫**兩層**：芯層 MAX、暈層加法 |
| `glow/GlowLayer.jsx` | React 包裝：量容器、建舞台、rAF 迴圈、淡入淡出、呼吸 | 舞台**不能**跟著 `rebuildKey` 重建 |

#### 為什麼是 ribbon 而不是 `THREE.Line`

要在「橫剖面」上做柔邊（中心緊、邊緣散），bloom 才有東西可以吃。
單純的線只有一個像素寬的核心，泛出來會很扁。

```js
export function ribbon(points, width, closed = false) {
  // 先算累積弧長，aT 才是【等弧長】而不是「第幾個點」——
  // 取樣疏密不均時後者會讓彗星忽快忽慢。
  const acc = new Float32Array(n)
  for (let i = 1; i < n; i++)
    acc[i] = acc[i-1] + Math.hypot(pts[i].x - pts[i-1].x, pts[i].y - pts[i-1].y)
  const total = acc[n-1] || 1
  // 每個點往法向左右各推 half，aSide = ±1，aT = acc[i] / total
  ...
  geo.userData.length = total   // ← 彗星速度與 draw-on 都用它換算
}
```

另外附一個 `circlePoints(cx, cy, r, step = 6)`——iPad 的節點外圈、桌面的 slot 圓環、中樞環都用它。

#### 兩層混色

> **凍結 — 芯層 MAX、暈層加法**
> 兩層不能用同一種混色。

```
芯層  MAX   // 8 垂直 × 4 水平 = 32 個交叉點。用加法會讓每個交叉點亮兩倍，
            // 整片背景框架的亮度就不統一。MAX 取較亮者，重疊處與單獨一條線一樣亮。

暈層  加法   // ⚠ 光暈【不能】用 MAX：那會算成 max(光暈, 背景)，
            // 比背景 #16181D 還暗的外圈全部被丟掉，光暈被砍成一條 6 單位寬的硬邊帶。
            //
            // 實測剖面（MAX）：
            //   …87, 90, 113, 155, 265, 626, 626, 265, 155, 114, 90, 87… 之後直接是背景 82
            // 改加法之後（連續衰減）：
            //   …157, 177, 201, 227, 260, 310, 426, 714, 714, 426, 310, 261, 227, 201, 177…
            //
            // 暈層在交叉點會相加，但它只有 0.3，比芯的 1.95 溫和得多。
```

實作：暈層先畫（`renderOrder 0`）、芯層後畫（`renderOrder 1`），共用同一份 geometry。

```js
// 芯層
blending: THREE.CustomBlending,
blendEquation: THREE.MaxEquation,
blendSrc: THREE.OneFactor, blendDst: THREE.OneFactor,

// 暈層
blending: THREE.CustomBlending,
blendEquation: THREE.AddEquation,
blendSrc: THREE.OneFactor, blendDst: THREE.OneFactor,
```

**不能用 `THREE.AdditiveBlending`**——它是 `(SrcAlpha, One)`，而這裡的 alpha 已經改成「跟著亮度」，
再乘一次等於把光暈平方掉。要用預乘式加法 `(One, One)`。

#### `ridge()`：把亮芯撐到至少 N 個像素寬

`pow(cross, uSharp)` 的半高半寬約 `ln2 / uSharp`。線越細、指數越大，芯就越窄；
窄到比一個像素還細時，畫出來的亮度取決於「像素中心有沒有剛好落在芯上」。

```glsl
#ifndef MIN_CORE_PX
#define MIN_CORE_PX 1.0
#endif
float ridge(float c, float sharp, float dSide) {
  float d  = max(dSide, 1e-5);
  float s1 = min(sharp, 1.386 / d);                  // 2*ln2 / 一像素 → FWHM ≈ 1px
  float s  = min(sharp, 1.386 / (MIN_CORE_PX * d));  // FWHM ≈ MIN_CORE_PX px
  return pow(c, s) * (s1 / sharp);                   // 補償固定拿 s1 算，見下
}
```

> **踩過的坑 — 這一段最值錢**
>
> **（一）** iPad 的關聯邊線寬調細之後芯只剩 0.52px，近水平的線（0.6°）
> 每約 100px 才跨過一個像素列，於是每約 100px 亮一段暗一段——看起來就是「一節一節」。
> 陡的線每 1px 就跨一列，高頻反而看不出來。
> 實測峰值沿線 255→191→255→205…，峰值所在的像素列同時在 0 / −1 之間跳。
>
> **（二）撐到「剛好一像素」只治好線本身，治不好光暈。**
> UnrealBloomPass 的高通是比峰值：iPad 上芯的峰值 ≈ 1.15、threshold 才 0.5，餘裕只有一點；
> 亞像素對位差半個像素峰值就掉一半到 ≈ 0.57 貼在門檻上，那一段完全不泛光。
> *芯本身是連續的（隔離單條邊掃描，整條線都有 255 的像素），斷掉的是 bloom。*
> 1687×948 緩衝上實測 `edge-sensor-ac`（0.5°）：離線 12px 的光暈在 27↔50 之間起伏、週期約 140px
> ——那就是畫面上一顆一顆的光暈。
>
> **（三）亮度補償必須固定拿 `s1` 算。**
> 補償的用意是「線不要因為被撐寬而變亮」，以一像素為基準就夠了；
> 跟著 `s` 一起降會把峰值壓到 1/17，直接掉到 bloom threshold 以下、光暈整個消失
> （實測光暈平均值 24 → 3.6）。
>
> **實測值**：iPad 用 `minCorePx = 2.0`。
> 1.0 時光暈起伏 0.85、1.5 掉到 0.28、**2.0 是 0.22（最低）**，再往上只會讓線變粗變亮。
> 代價是亮帶從 3.7px 變成 7.8px、光暈亮度約 2 倍。
>
> 牆面與桌面**不帶**這個 define（＝1.0，行為與加這個功能前逐字相同）——
> 牆面的格線是 `VLINES` / `HLINES`，純水平垂直，沿線的亞像素相位根本不變。
>
> **注意**：`MIN_CORE_PX` 一定要帶小數點。GLSL ES 100 不會把 int 自動轉 float，`2 * d` 會編不過。
> 用 `minCorePx.toFixed(2)`。

#### 發光線 fragment

```glsl
uniform vec3  uColor;
uniform float uAmp;        // 這一層的亮度（芯層用 core、光暈層用 soft）
uniform float uSharp;      // 這一層的收斂指數
uniform float uGain;       // 整體倍率：家電框 active 時拉高、呼吸也乘在這裡
uniform float uAlphaLuma;  // 0 = alpha 恆為 1（牆面）；1 = alpha 跟著亮度（iPad / 桌面）
varying float vSide;

void main() {
  float cross = max(0.0, 1.0 - abs(vSide));
  vec3 c = uColor * uAmp * ridge(cross, uSharp, fwidth(vSide)) * uGain;
  float a = mix(1.0, clamp(max(max(c.r, c.g), c.b), 0.0, 1.0), uAlphaLuma);
  gl_FragColor = vec4(c, a);
}
```

`uAlphaLuma` 的必要性：iPad / 桌面的 canvas 是透明的、疊在平面圖與面板之上；
若 alpha 恆為 1，一條 `uGain=0` 的線（＝沒感應、應該看不見）仍然會把整條 ribbon 的
alpha 寫成 1，變成一條不透明的黑帶蓋住底下的平面圖。
**實際踩過**：iPad 上出現一整片灰色的網格，就是所有 idle 的關聯邊在蓋圖。

#### 彗星 fragment

```glsl
// 一顆彗星在位置 vT 的亮度。
// prog < 0 = 這一輪還沒發射 → 整顆不畫（不是停在起點！路徑兩端就是黑塊邊緣，
// 停在起點會變成一顆亮點杵在家電框邊上）。
// 頭部從 0 掃到 1 + uTailSpan：掃過 1 之後頭已經出了核心邊緣不再畫，
// 尾巴繼續往前掃出去，整條尾巴才會乾淨地沒入核心，而不是突然消失。
float cometAt(float ph, float t) {
  float prog = (ph - (1.0 - uTravel)) / uTravel;
  if (prog < 0.0) return 0.0;
  float d = prog * (1.0 + uTailSpan) - t;    // > 0 表示在頭部後方
  if (d < 0.0) return 0.0;
  return max(0.0, (exp(-d / uTailLen) - 0.04) / 0.96);
}

void main() {
  // 同一條線上跑 COMETS 顆，相位平均錯開。取 max 而不是相加 ——
  // 兩顆疊在一起時相加會爆掉，看起來像一團白。
  float base = uTime / uCycle + uPhase;
  float trail = 0.0;
  for (int i = 0; i < COMETS; i++)
    trail = max(trail, cometAt(fract(base + float(i)/float(COMETS)), vT));

  // 橫剖面：中心緊、邊緣柔
  float cross = max(0.0, 1.0 - abs(vSide));
  float dSide = fwidth(vSide);
  float core = ridge(cross, uCoreSharp, dSide);
  float soft = ridge(cross, uSoftSharp, dSide);

  // 三階顏色：深藍 → 青 → 白
  vec3 col = mix(uTail, uBody, smoothstep(0.0, 0.35, trail));
  col = mix(col, uHead, smoothstep(0.55, 1.0, trail));

  // 底光：感應期間整條線持續亮著，並隨呼吸緩慢明暗。
  // 亮芯 + 一點柔邊，只有柔邊的話整條線會糊成一條霧、看不出是「線」。
  float baseLit = uBase * uBreathe * (core + uBaseSoft * soft);

  // ⚠ 彗星不乘呼吸：它是資料封包，跟著明暗會讀成訊號不穩。
  float amount = baseLit
               + uPeak * core * trail
               + uHeadBoost * core * pow(trail, uHeadSharp);  // ← 超過 1.0 就是 bloom

  // 兩端各淡出一小段：ribbon 切在黑塊邊緣，不淡的話會看到硬切邊
  float ends = smoothstep(0.0, uEndFade, vT) * smoothstep(1.0, 1.0 - uEndFade, vT);
  amount *= ends * step(vT, uProgress) * uOn;

  vec3 c = col * amount;
  float a = mix(1.0, clamp(max(max(c.r, c.g), c.b), 0.0, 1.0), uAlphaLuma);
  gl_FragColor = vec4(c, a);
}
```

`COMETS` 必須是編譯期常數（GLSL ES 100 的 for 迴圈上限不能是 uniform）。

#### 彗星參數（`SHARED.comet`，單位是「畫面寬的幾分之幾」）

| 參數 | 值 | 意義 |
| --- | --- | --- |
| `count` | 2 | 每條線同時跑幾顆，相位平均錯開 |
| `speed` | 0.2609 | 每秒走過幾分之幾的畫面寬（× 1610 ＝ 牆面 420 單位/秒） |
| `minCycle` | 2.0 s | 一輪最短秒數。短線不要一直發射，會很吵 |
| `travelMax` | 0.7 | 飛行最多佔一輪的比例，其餘時間彗星在線外＝封包之間的間隔 |
| `tailWidths` | 0.1025 | 拖尾 e-fold 長度 ÷ 畫面寬（× 1610 ＝ 165 單位） |
| `tailMaxFrac` | 0.6 | 短線上不能超過這個比例，不然整條線都是尾巴 |
| `breathe` | 1.5 s | 底光呼吸一輪（牆面背景框架是 3.0 s） |
| `breatheLo` | 0.5 | 最暗時的倍率（1 = 最亮） |

換算：

```js
const tailLen   = Math.min(tailUnits / len, tailMaxFrac)
const tailSpan  = tailLen * 3.22          // exp 衰減到 0.04 需要 ln(25) ≈ 3.22 個 tailLen
const travelSec = ((1 + tailSpan) * len) / speed
const cycle     = Math.max(travelSec / 0.7, minCycle)
const uPhase    = (index * 0.37) % 1      // 定值相位，不用 Math.random
```

拖尾長度用**世界單位**而不是路徑比例——牆面九條線的可見長度差 5 倍以上
（`socket` 118、`sensor` 652），用比例的話每條線的彗星看起來會不一樣長。
速度則是**九條一律同速**，長線自然跑比較久；短線靠 `minCycle` 拉長等待而不是拉長飛行。

相位用索引推出的定值而不是 `Math.random`——每次載入都要一樣。

#### Bloom

```js
bloom: { strength: 1.15, radius: 0.62, threshold: 0.5, softKnee: 0.55 }
```

- `threshold`：只有超過這個亮度的像素才泛光。調高 → 只有彗星頭發亮；調低 → 連底光與格線都糊成一片。
- `softKnee`：門檻的「軟硬」。UnrealBloomPass 預設 0.01 幾乎是硬切——
  亮度一跨過 threshold 泛光就整個冒出來，呼吸時看起來就是一頓一頓的。
  拉寬之後泛光是隨亮度漸漸長出來的，呼吸才會滑順。

```js
bloom.highPassUniforms.smoothWidth.value = B.softKnee
```

#### 渲染管線的三個死規則

> **凍結**
>
> **1. 顏色一律用 `col()` 建，不要 `new THREE.Color('#xxxxxx')`。**
> ```js
> export function col(hex) {
>   return new THREE.Color().setHex(parseInt(hex.slice(1), 16), THREE.LinearSRGBColorSpace)
> }
> ```
> `outputColorSpace` 是 Linear（整條管線＝不做色彩管理、值原樣顯示），
> 而 `new THREE.Color('#7FE3FF')` 會把 sRGB 轉成 linear，
> 螢幕上會比色碼暗一大截，而且背景會跟 CSS 對不起來。
>
> **2. 不要「順手改回 `SRGBColorSpace`」。**
> three 把場景畫進 EffectComposer 的中繼緩衝時就已經編成 sRGB 了，
> 這裡若維持預設，`OutputPass` 會再編一次——整張畫布會霧成一片灰。
> ```js
> renderer.outputColorSpace = THREE.LinearSRGBColorSpace
> composer.renderTarget1.texture.colorSpace = THREE.LinearSRGBColorSpace
> composer.renderTarget2.texture.colorSpace = THREE.LinearSRGBColorSpace
> ```
>
> **3. 所有材質必須 `DoubleSide`。**
> 正交相機 `top=0 / bottom=H` 讓 y 向下（與 CSS / SVG 同向），
> 代價是投影矩陣的 y 是負的、三角形環繞方向跟著翻——
> 用 `FrontSide` 畫得出 draw call 卻一個像素都不會出現。
>
> **附帶**：`premultipliedAlpha` 必須 `true`（shader 輸出的 alpha 是該像素亮度，
> 色值沒再除以 alpha，那正是已預乘的形式；設 false 瀏覽器合成時會再乘一次，
> 暗的地方等於被平方，整層光會明顯變暗）。
> `toneMapping = THREE.NoToneMapping`——彗星頭超過 1.0 的部分直接夾成純白，亮度交給 bloom 表現。

#### 緩衝固定面積，不固定寬度

```js
const AREA = (PARAMS.refWidth * PARAMS.refWidth) / 1.6   // ≈ 1600×1000 = 1.6 MP
const H = Math.round(Math.sqrt(AREA / aspect))
const W = Math.round(H * aspect)
```

> **踩過的坑**
> 一開始是固定寬度 `W = refWidth, H = refWidth / aspect`。容器一旦變得又窄又高
> （例如視窗縮到資訊面板把中樞區擠成一條），H 會爆掉——
> 實測 aspect 0.24 時緩衝變成 1600×6667 ＝ **10.6 MP**、幀時間掉到 21ms，
> 而且 UnrealBloomPass 的橫向／縱向模糊是各自相對於 `resolution.x / y` 的，
> **非方形緩衝會把光暈拉成直立的橢圓**。
>
> 而且**內部緩衝固定、CSS 尺寸才跟著容器走**。若讓緩衝跟著 CSS 尺寸跑，
> 小視窗裡每條線只剩 1px，bloom 的粗 mip 會把它們攤成一層霧；
> 固定之後不管在多大的視窗看都一樣，調參數才有意義。

`dpr` 也鎖 1，不用裝置的 `devicePixelRatio`——bloom 本來就是模糊，
降採樣幾乎看不出來，但成本差四倍。這是效能的第一道保險。

#### 像素相位對齊（牆面專屬）

> **踩過的坑**
> 軸對齊的線要對齊到同一個像素相位，否則同樣的設定會畫出兩種粗細與亮度。
>
> 實測：大框上下緣在 y = 47.5 / 1032.5（半整數）＝正好落在*像素中心*，
> 峰值全部集中在一個像素上（剖面 81 / 263 / 742 / 263 / 81）；
> 而格線與大框左右緣都是整數＝落在*像素邊界*，峰值被兩個像素平分
> （剖面 141 / 493 / 493 / 141）。於是只有上下兩條看起來又亮又銳利。
>
> **而且要對齊到「偶數」，不是整數就好。**
> UnrealBloomPass 的第一層降採樣是 1/2 解析度，落在奇數座標的線會剛好對上
> 半解析度的紋素中心、能量被集中起來，泛光比偶數座標的線強 6 成。
>
> 實測（關 bloom 時每條線都是「峰 631 / 暈總量 2294」完全相同）：
> 開 bloom 後 y=335（奇）暈總量 3839、x=1435（奇）3801，
> 而 y=550 / x=1600 / 大框頂（偶）只有 2353 / 2377 / 2351。
> 全框架只有 x=1435、y=335、大框下緣 y=1033 是奇數——正好就是看起來比較亮的那三條。
>
> ```js
> const snap = (v) => 2 * Math.round(v / 2)
> ```
>
> **只對大框與格線做。** 家電框／核心框的外圈**不能動**——
> 它們必須與 SVG 黑塊的邊界對齊，差 0.5 就會露出來。
> 另外，「整數 = 像素邊界」成立的前提是內部緩衝固定 1920×1080（`FX.dpr = 1`）。

#### GlowLayer 的三件事

```js
// 1. 舞台【不能】跟著 rebuildKey 重建
//    在同一張 canvas 上重複 new WebGLRenderer 會留下前一個 context
//    （Chrome 大約 16 個就開始強制回收最舊的），拖一次滑桿就重建一次的話很快就會掉 context。
//    尺寸變 → 重建舞台；只有幾何變 → 只換場景內容。

// 2. 量容器要能重試
//    containerRef 指的是【父層】的 div，而 React 的 commit 是深度優先：
//    子元件的 useLayoutEffect 會在父層的 ref 掛上去【之前】就跑，
//    第一次進來時 containerRef.current 常常還是 null。
//    ⚠ 重試用 setTimeout 而不是 requestAnimationFrame ——
//      分頁在背景時 rAF 會被凍住，那樣發光層要等到分頁被看見才會初始化。

// 3. activeIds 走 ref、不進依賴陣列
//    每次刷卡都重建場景會把彗星的相位打回原點，看起來像整組線閃一下。
```

淡入淡出：

```js
const EASE = 6   // 收斂速率（每秒）
st.on += (want - st.on) * Math.min(1, dt * EASE)
if (Math.abs(want - st.on) < 0.02) st.on = want   // ⚠ 門檻要鬆，不然會留一絲永遠不熄的殘影

// 呼吸：全部同相位 —— 讀起來是「一個系統在運轉」，而不是各自閃各自的
const wave = (period, lo) => lo + (1 - lo) * (0.5 + 0.5 * Math.cos((time * 2 * Math.PI) / period))
```

WebGL 起不來或 context lost 時**安靜退場**（`canvas.style.display = 'none'`）——
面板、文字、平面圖仍然正常，不要讓一顆 GPU 打掉整個畫面。

## 4. 介面材質與特效

毛玻璃是三端唯一「靠 token 統一而不是靠同一套繪圖」的東西，所以配方要寫得很清楚。

### 4.2 三端的玻璃變體

#### 牆面 — `.panel-glass` ＋ `.panel-glass-rim`

跑在 SVG `<foreignObject>` 裡（`backdrop-filter` 對 `<rect>` 完全無效）。
實測 foreignObject 內 **1 CSS px ＝ 1 viewBox 單位**，
所以 blur / 圓角 / 陰影都會跟著投影自動縮放，不需要任何換算。

```css
.panel-glass {
  position: relative;             /* 供 .panel-glass-rim 定位 */
  width: 100%; height: 100%;
  border-radius: 12px;            /* = RADIUS.md */
  background: var(--glass-bg);
  backdrop-filter: var(--glass-blur);
  border: 1px solid var(--glass-border-flat);
  box-shadow:
    0 10px 30px rgba(0, 0, 0, 0.55),
    inset 0 1px 0 rgba(255, 255, 255, 0.42);
}
.panel-glass-rim {                /* ⚠ 是 .panel-glass 的【子元素】 */
  position: absolute; inset: 0;
  border-radius: inherit;
  pointer-events: none;
  border: 1px solid var(--glow-rim);
  box-shadow:
    0 0 14px var(--glow-halo),                /* 外緣光暈 */
    inset 0 0 12px rgba(255, 255, 255, 0.1);  /* 內緣霧光 */
  opacity: 0.8;
}
```

高光邊是*子元素*（＝畫在玻璃之上）是刻意的：
它就不屬於玻璃的 backdrop，`opacity` 動起來不會害 `backdrop-filter` 每幀重算。
外暈 14px 遠小於 `PLATE_PAD`（40），不會被 foreignObject 裁掉。

#### 桌面 — `.info-panel`

刻意**拿掉 `--glass-shadow` 的第一層**（`0 10px 30px rgba(0,0,0,0.55)`），其餘三層原樣照抄。

> **踩過的坑**
> 那層黑投影是為「純深色平底」設計的（近黑底上壓 40% 黑 = 看不見）。
> 這一端加了背景漸層之後，面板周圍的底有了亮度與顏色，同一條黑帶就浮出來，
> 變成資訊面板與感應區之間一條很硬的分界。
>
> 實測遮蔽率：
> - 下緣外 0px 40% / 10px 27% / 20px 13% / 30px 5%
> - 右側外 0px 27% / 10px 13% / 20px 5%
>
> （下緣是右側的 1.5 倍，因為那個 10px 是向下偏移——看起來就像面板底下墊了一塊深色底。）
>
> 順帶一提：CSS `box-shadow` 的**第一層畫在最上面**，所以原本那圈藍色 rim 一直被黑色壓著，
> 本來該是「發光的邊」變成「暗邊帶一點藍」。拿掉之後才是原本設計的樣子。
>
> ⚠ 這是桌面專屬的覆寫。`--glass-shadow` 由 `sync-tokens.mjs` 產生（黑色那層寫死在產生器裡），
> 所以牆面那邊如果調了 `glass.haloBlur` / `glass.rimOpacity`，這裡要**手動同步**。

#### iPad — `.acard` / `.detail__card`

卡片壓在俯視照片上，backdrop 真的有東西可以糊——那是「透出下面的房間」的來源。
除了模糊之外還做了三件事，**少任何一件都會退回「半透明色塊」而不是玻璃**：

1. backdrop 加 `brightness(0.82) contrast(1.05)`——玻璃會把背後的東西壓暗一點、彩度提一點
2. 一層很淡的**深色** tint `rgba(12,16,22,0.34)`（不是純白）——
   照片亮的地方（木地板、燈光）直接透上來會把白字吃掉，這層負責保住可讀性
3. `::after` 的 118° 斜向鏡面高光——這是「看起來是一片玻璃」的關鍵

```css
.acard {
  overflow: hidden;
  background:
    linear-gradient(180deg, rgba(255,255,255,0.10), rgba(255,255,255,0.03)),
    rgba(12, 16, 22, 0.34);
  border: 1px solid var(--glass-border-2);
  border-radius: 12px;
  backdrop-filter: var(--glass-blur) brightness(0.82) contrast(1.05);
  box-shadow:
    var(--glass-shadow-2),
    inset 0 -1px 0 rgba(0, 0, 0, 0.35);   /* 下緣暗邊＝玻璃的厚度 */
}
.acard::after {
  content: '';
  position: absolute; inset: 0;
  border-radius: inherit;
  pointer-events: none;                    /* ⚠ 卡片是 <button>，這層不能吃掉點擊 */
  background: linear-gradient(118deg,
    rgba(255,255,255,0.16) 0%,
    rgba(255,255,255,0.05) 26%,
    rgba(255,255,255,0)    46%,
    rgba(255,255,255,0)    72%,
    rgba(255,255,255,0.07) 100%);
}
/* active：玻璃更亮一階 + 淡藍高光邊 + 外緣光暈，tint 同時壓淡讓房間透更多上來 */
.acard--active {
  border-color: var(--glass-border);
  background:
    linear-gradient(180deg, rgba(255,255,255,0.16), rgba(255,255,255,0.05)),
    rgba(12, 16, 22, 0.26);
  box-shadow: var(--glass-shadow), inset 0 -1px 0 rgba(0,0,0,0.3);
}
```

圓角要跟 `::after` 一致（`border-radius: inherit`），不然高光會溢出圓角。

> **踩過的坑 — `.acard` 那條規則裡不要寫 `position`**
> 版面靠 `absolute` 定位，在同一條規則裡再寫 `relative` 會蓋掉它，
> 卡片會整排掉回文件流擠在左邊。

### 4.3 面板進場：兩層結構

> **凍結 — 玻璃底板不能放在會動 `opacity` 的群組裡面**
>
> 規格上 `opacity < 1` 的祖先會建立一個新的 backdrop root，`backdrop-filter` 於是取樣不到任何背景
> ——玻璃在整段動畫期間等於沒有模糊也沒有壓暗，背後的框架格線就一條一條銳利地穿透過來，
> 動畫結束那一幀才「啪」地變成玻璃。
> **實測 opacity 只要從 1 掉到 0.99 就足以觸發**，不是掉幀也不是快取沒暖。
>
> **解法**：拆成兩層——玻璃在外層（永遠 opacity 1，出現即最終樣貌），
> 引線與文字在內層淡入淡出。
> 代價是底板本身「啪」一下出現——而那正是要的：面板一出現就已經是最上層的視覺狀態。
>
> ```jsx
> <motion.g>
>   <GlassPlate x={px} y={py} w={PW} h={PH} />   {/* 外層，不動 opacity */}
>   <motion.g initial={{ opacity: 0 }} animate={{ opacity: 1 }} exit={{ opacity: 0 }}
>             transition={{ duration: MOTION.dur, ease: MOTION.ease }}>
>     {/* 引線、標題、資料列 */}
>   </motion.g>
> </motion.g>
> ```

**而且進出場只做不透明度、不做位移。**
會動的 `backdrop-filter` 元素是最貴的情況——元素每移動一格，
合成器就得把底下那塊背景重讀一次再模糊一次。
九個面板同時進場（全部刷卡的那一刻，也就是這個互動的高潮）正好是最壞情境。
位置固定、只變 alpha 的話背景取樣可以重用。視覺上玻璃「就地浮現」也比滑進來更像玻璃。

掛載／卸載要用 `AnimatePresence`——元件自己 `return null` 會直接消失，沒有淡出。

### 4.4 桌面的流動漸層背景

三個色點各自往外散成一團柔光，疊起來就是 Adobe 那種任意形狀漸層。

用三個 `<div>` ＋ `radial-gradient`，**不是** canvas 也不是 shader——
色團只要光柵化一次，之後每一幀只是合成器把同一張圖位移幾個像素，沒有重繪、沒有版面計算。
這一端已經有一個 WebGL context 在跑發光層了，不值得為背景再開一個。

| 參數 | 值 | 為什麼是這個值 |
| --- | --- | --- |
| `spread` | 100 vmin | 62 時三個色團的聯集**蓋不滿畫面**，左側有 11.5% 的面積完全在色團之外＝純底色、一點漸層都沒有，而那塊死區正好貼在資訊面板右緣。實測死區比例 62→11.5% / 70→6.3% / 80→2.9% / 90→0.6% / **100→0%** |
| `strength` | 0.45 | 整體不透明度。顏色本身只管色相，濃淡一律由這個調 |
| `drift` | 9 vmin | 2～3 太小——那個幅度在 1080 高上只有 ±30px，看起來是靜止的。9 ＝ ±97px，一來一回約 190px，是「在流動」而不是「在飄」 |
| `speed` | 1.4 | 1 ＝ 每個點約 26～38 秒繞一圈 |
| 點 1 的 x | 34% | 見下 |

> **踩過的坑 — 點 1 為什麼從 66% 搬到 34%**
> 三個點都偏右時最暗的區域是整個左半邊，而資訊面板蓋掉 x 1.5%–30%，
> 剩下 30%–37% 那條窄縫是那塊暗區**唯一露出來的部分**，
> 夾在亮面板與逐漸變亮的感應區之間，看起來就是一條貼著面板的深色帶。
>
> 實測平均亮度（0–255）：
> - 點1 在 66%：窄縫 34.7 / 感應區 49.0 → 落差 −14.3
> - 點1 在 34%：窄縫 43.3 / 感應區 44.1 → 落差 −0.8
>
> 代價是面板背後從 32.2 亮到 40.6，毛玻璃會透一點過去。
> 實測 WCAG 對比：主文字 11.6 → 10.3、次階文字 5.5 → 5.0，都還遠高於 AA(4.5)。
> 但**不要再往面板中央拖**：拖過去對比就會開始掉出安全範圍。

> **踩過的坑 — 徑向衰減不要寫成「顏色 0% → 透明 100%」**
> 那是*線性*斜坡：半徑內斜率固定、半徑外是 0，交界處是一個折角。
> 亮度本身是連續的，但人眼對「斜率的不連續」極度敏感（Mach band）
> ——結果就是在色團邊緣看到一條根本沒有畫出來的邊。
> 實測折角處亮度斜率從 0 跳到 3.36（每 100px），那條線正好落在資訊面板右側，
> 看起來就是「面板邊緣有一塊深色塊」。
>
> 用 smootherstep 取樣之後邊緣斜率趨近 0，折角就沒了。
> 取樣點還要**不等距**（越靠近邊緣越密）——
> CSS 漸層停駐點之間是線性內插，等距取樣在最後一段仍然會留下可見折角。
>
> ```js
> const STOPS = [0, 0.15, 0.3, 0.45, 0.6, 0.72, 0.82, 0.9, 0.94, 0.97, 0.99, 1]
> const ease  = (t) => 1 - (3 * t * t - 2 * t * t * t)
> const falloff = (color) =>
>   STOPS.map((t) => `${color}${hex2(ease(t))} ${+(t * 100).toFixed(1)}%`).join(', ')
> ```

其他實作要點：

```js
// 晃動只動 transform，不動 left/top（後者會觸發 layout + paint）
// 兩個不同週期的正弦 = 一個緩慢的李薩如軌跡，比正圓自然
const ORBITS = [
  { px: 29, py: 37, phase: 0   },
  { px: 34, py: 26, phase: 2.1 },
  { px: 38, py: 31, phase: 4.3 },   // 週期刻意互質一點，不然三個點會週期性同時回到原位
]
const dx = Math.cos((t * 2 * Math.PI) / o.px + o.phase)       * drift
const dy = Math.sin((t * 2 * Math.PI) / o.py + o.phase * 1.7) * drift
el.style.transform = `translate(calc(-50% + ${dx}vmin), calc(-50% + ${dy}vmin))`
```

- 位移單位是 **vmin 不是 %**——`translate` 的百分比是相對*元素自己*的尺寸，
  用 % 的話調大色團就會連帶晃得更遠，那不是這支滑桿該有的意思。
- 色團尺寸也用 vmin——% 會分別對上容器的寬與高，畫面一寬色團就被拉成橢圓。
- 色團自己**不要加 `filter: blur()`**：`radial-gradient` 本身就是柔的，
  加了等於要求合成器每次位移都重做一次大面積模糊，
  那正是「背景會動」變成「整個介面掉幀」的原因。
- 編輯模式要把晃動**凍結**並歸零（不是停在當下那一格）——
  停在半路的話編輯器上顯示的座標會跟眼睛看到的差一個位移。

## 5. 牆面規格

16:9 投影，`viewBox 1920×1080`。這一端的座標**是物理**——改了現場的實體展品就對不上位置。

### 5.1 畫面組成

- **十一個純黑挖空框**——九台家電 ＋ 中樞 ＋ 電視預留區。這些是牆上實體展品的預留位。
- **背景框架**——大框（圓角矩形）＋ 12 條正交格線，恆亮並緩慢呼吸（3 秒一輪）。
- **走線**——家電框 → 中樞框，感應時亮起並跑彗星。
- **狀態面板**——active 時在家電框旁彈出的毛玻璃面板：家電名、設備代碼、狀態列、資料列。
- **家電照片**——框內放對應家電的去背 WebP，佔框的 88%，idle 0.5 / active 0.95 不透明度。

> **凍結 — 三個「不是樣式、是物理」的東西**
> 1. `viewBox="0 0 1920 1080"`——座標系本身。
> 2. `preserveAspectRatio="xMidYMid meet"` ＋ `width/height 100%`——
>    換成 `slice` 或加上任何 padding / header，九個黑框會整體位移。
> 3. 黑框與電視預留區的 `fill="#000"`。
>
> 而 `.wall-stage { position: fixed; inset: 0; display: flex; align-items: center; justify-content: center }`
> 也是結構性的，加任何 padding / border 都會整體縮放。

### 5.4 家電照片

```js
const IMG_FIT = 0.88
const BLOCK_IMG = { idle: 0.5, on: 0.95 }
```

產生方式（換圖時照這個做，不然檔案會胖回去）：

- 尺寸 ＝ 該黑塊**實際繪製尺寸**的 2 倍，不是統一 720。
  繪製尺寸 ＝ `min(w × IMG_FIT / 圖寬, h × IMG_FIT / 圖高) × 圖尺寸`（因為是 `meet`）。
  原本統一 720 時，九張存的是實際繪製尺寸的 2.2～4.4 倍，純浪費。
- 格式 ＝ WebP quality 92（method 6）。
  實測九張與無損版比，可見區的 RGB 平均差 < 1.3/255，而**alpha 逐像素完全相同**
  ——去背邊緣沒有被壓壞，那是這裡最要緊的部分。
  無損 WebP 687 KB、q92 90 KB（原本 PNG 2411 KB）。

照片只佔框的 88%、不貼齊邊緣：框是實體展品的預留位，
照片貼齊邊會讓框線與照片黏在一起，看不出「框」。

> **注意**：這九張是**投影出來的光**，不是貼圖裝飾。
> 黑塊原本的用途是「不出光，讓牆上的實體展品不被打亮」；放了照片之後那一格就會亮起來。
> 展場如果實體展品還在原位，這裡要調暗甚至關掉（`BLOCK_IMG`）。

路徑一定要串 `import.meta.env.BASE_URL`——GitHub Pages 的專案站掛在子路徑底下，
寫死 `/appliances/x.webp` 會 404。

### 5.5 自動佈線（`routing.js`）

規則就一句：**從家電黑塊邊緣走到核心黑塊邊緣。** 實作上分兩條路徑：

| 路徑 | 範圍 | 用途 |
| --- | --- | --- |
| `visible` | 兩端都切在黑塊邊界上，中間沒有任何藏起來的線段 | 真正畫出來的 ribbon |
| `full` | 兩端各自伸進黑塊裡面（`SWALLOW = 170`） | 彗星的運動軌跡 |

> **踩過的坑**
> 舊版是把 ribbon 蓋在完整路徑上、讓黑塊把兩端蓋掉（彗星就有地方躲）。
> 問題是**黑塊只蓋得住畫面，蓋不住 bloom**——躲在核心黑塊裡的彗星仍然會泛光，
> 那圈光會從黑塊四周漏出來，看起來就像有東西在黑塊後面繼續跑。
> 現在路徑本身就到邊緣為止，彗星的生滅改由 shader 的相位控制。

#### 接點與避讓

```js
const SWALLOW = 170   // 彗星抵達核心後還要往裡面跑多遠才算完全被吃掉（> 頭半徑 + 拖尾長度）
const CLEAR   = 30    // 走線與「別人的黑塊」之間要留的淨空
const SNAP    = 12    // 接點與家電座標只差一點點時就吸過去
FX.corner     = 18    // 轉折處圓角半徑（逐個轉角夾到相鄰段的一半）
FX.beam.segments = 320
```

- **接點（pad）** ＝「核心中心 → 家電中心」這條射線與核心黑塊邊界的交點。
  九個接點自然沿方位放射分布在三條邊上，不需要另外排序、也不會互相撞。
  最後一段一律垂直插入該邊。
- **`SNAP = 12`**：`socket` 在 x=960、射線打出來是 957.4，不吸的話末段會多一個
  2.6 單位的 S 形小折，投影出來就是一個看得見的疙瘩。
- **`CLEAR = 30`**：線貼著框邊走會讀成「線黏在展品上」，而投影距離下 8 這種等級
  根本看不出是刻意留的空隙。30 與面板離框距離（`GAP = 22`）同一個量級。
  命中測試改用「膨脹框」（`inflate(b, CLEAR)`），避讓後自然就有淨空，不必再另外加 margin。
  **資訊面板不算障礙物**——線可以直接穿過面板。
- **`unGraze()`**：處理主幹「擦過自己的框」的兩種難看情況——
  (a) 落在框外但貼著邊（沿框邊擦過去）、(b) 落在框內但太靠近要穿出去的那條邊（從框角切出去，像削到角）。
  乾淨的走法只有兩種：夠深入框內（從邊的中段垂直穿出），或離框至少 `CLEAR`。
- **電視預留區也要檢查**。規格明訂「不准有連線穿過」；
  舊版的自動佈線完全沒檢查它，只靠上排兩台剛好沒經過而已。
- **手動覆寫**：`appliances.js` 可加 `route: [[x,y], ...]`（不含起點與 pad）。
  有 route 的就完全照給的點走、不再自動避讓。
  dev 模式下會檢查每段是否為八方位（0/45/90），不合的在 console 提示。

曲線用 `CatmullRomCurve3`（centripetal）取樣——`getSpacedPoints()` 給**等弧長**取樣，
ribbon 的寬度與彗星的速度才會沿線一致（直接用原始取樣點的話疏密不均）。
輸入點已經很密（圓弧每 3 單位、直線每 24 單位），內插誤差實測 < 0.02%。

### 5.6 狀態

| 狀態 | 家電框 | 走線 | 面板 | 照片 |
| --- | --- | --- | --- | --- |
| **idle** | 全暗（`blockIdle = 0`） | 不畫 | 無 | opacity 0.5 |
| **active** | 亮起並呼吸（`blockOn = 1.9`，1.5 s 一輪） | 底光 ＋ 彗星 | 淡入 | opacity 0.95 |

家電框與中樞框在沒感應時是**完全不發光**的——那時它只是一塊黑，等卡片來才亮。
背景框架則一直亮著，兩者是不同的呼吸週期（3.0s / 1.5s）。

`FX.svgBlockStroke = false`：SVG 那層完全沒有白框，所有輪廓都來自 canvas 的發光外圈。
關掉之後「呼吸」完全由光暈承擔——之前覺得呼吸僵硬就是因為那條硬白線恆亮、主體不動。
（黑底本身不能拿掉：它負責蓋住往框內溢的 bloom。）

### 5.7 發光層參數（`FX`）

```js
LINE_W = 3, LINE_W_IDLE = 2

FX.beam = {
  width: 26,        // ribbon 總寬（世界單位）。芯只佔中間一小條，其餘是柔邊給 bloom 吃
  coreSharp: 7.0,   // 橫剖面收斂指數：越大芯越緊、邊越柔
  softSharp: 1.6,   // 外圍柔光的指數（比 coreSharp 小很多，才會有一圈暈）
  segments: 320,
  speed: 0.2609 * 1610,      // ≈ 420 單位/秒
  tailUnits: 0.1025 * 1610,  // ≈ 165
  endFade: 6,       // 兩端各淡出幾個單位，避免 ribbon 被切斷的硬邊
  base: 0.75,       // 導線底光（感應期間整條線持續亮著）＝ 最亮時的值
  baseSoft: 0.35,   // 底光有多少比例攤在柔邊上。太高整條線會糊，太低就只剩一條硬線
  peak: 1.1,        // 彗星身部的亮度
  headBoost: 1.8,   // 頭部再往上加多少 —— 超過 1.0 就是 bloom 的來源
  headSharp: 26,    // 頭部沿線的集中度。要調小顆要「headBoost 降 + headSharp 升」兩個一起動
}

FX.frame = {
  width: 27,        // ribbon 總寬。光暈的最大擴散半徑就是 width/2
  coreSharp: 17.0,  // ⚠ 是「相對於半寬」的指數，width 改了就要跟著改
  softSharp: 2.2,
  core: 1.95,       // 亮芯亮度（芯層是 MAX、暈層是加法，芯不吃到 soft 那一份，所以要比拆開前高）
  soft: 0.3,        // 外圍柔光亮度 —— 這一項就是「光暈」的主體
  breathe: { period: 3.0, lo: 0.55 },   // 背景框架自己的呼吸，與家電那組（1.5s）分開
  blockIdle: 0,     // 家電框沒感應時完全不發光
  blockOn: 1.9,
  hubIdle: 0,
}

FX.drawSpeed = 1400   // 點亮時「射向中樞」的速度（單位/秒）
FX.dpr = 1
```

`coreSharp` 與 `width` 的關係：26 寬配 17 ≈ 亮芯 1 單位（與舊的 14 寬配 9 相同）；
27 只差 3.8%，芯跟著粗 3.8%，看不出來，所以 `coreSharp` 維持 17。

九台**同相位**（同時呼吸）——這是「一個系統在運轉」的讀法。
想讓九台各呼吸各的，把算 breathe 的 time 加上 `phaseOf(i) * period` 就好。

```js
export const phaseOf = (i) => (i * 0.37) % 1   // 定值，不用 Math.random
```

### 5.8 狀態面板排版

```js
PW = 220, PH = 116        // 自動版面的預設尺寸（PANEL_LAYOUT 會覆寫）
GAP = 22                  // 面板離家電框的間隙
DODGE_MG = 8              // 避讓時與鄰框留的安全間距
PLATE_PAD = 40            // foreignObject 要比面板大這個的兩倍

PANEL_TEXT = { title: 15, rowGap: 15, stackedRatio: 34/25 }
PANEL_PAD  = { t: 10, r: 12, b: 8, l: 12 }
TITLE_ASCENT = 1.0

S = { title: TXT.title, code: 6.25, state: 6.5, key: 7.5, val: 8 }

innerW  = PW - P.l - P.r
yTitle  = py + P.t + S.title * TITLE_ASCENT   // 基線從內距＋字級推出來，不是寫死
yMeta   = yTitle + 12
yRule   = yMeta + 6
rowTop  = yRule + 11
avail   = py + PH - P.b - rowTop
maxRows = clamp(floor(avail / ROW_GAP), 1, 5)
```

> **踩過的坑 — `TITLE_ASCENT = 1.0` 不是隨手取的**
> 實測這組中文字的實際 ascender 約 0.97 em。
> 用 0.8 的話「上緣的實際留白」會隨字級變小（字級 12.5 留 5、26 只留 2.5，再大就頂出面板），
> 內距這個數字就不老實了。取 1.0 之後留白恆等於上內距。

> **踩過的坑 — 行距是固定值，不依高度平均分佈**
> 平均分佈會讓每塊面板行距都不一樣（實測 sensor 12、bathfan 13、其他 27~28），
> 整面牆看起來就不齊。

> **踩過的坑 — `rows` 的順序有意義**
> 面板高度不夠時只畫得下前幾列（最多 5），矮面板會截到只剩 2 列
> ——目前 `sensor` 與 `bathfan` 就是 2 列。所以**最重要的資訊一定要排在最前面**。
> `socket` 的前三列刻意是「設備耗電排行」而不是電氣讀值，就是這個原因。

標題字級用 `S.title`（上限）而不是 `fitLabelSize` 的結果來算基線：
名字長的面板字會縮小，但九塊面板的標題基線要對齊在同一條線上，整面牆才不會參差。

```js
// 標題字級自動縮放：家電名稱長度不一（「燈」1 字 ～「12合一感測器」7 字）
// 半形字（數字 / 英文）約佔全形的 0.55 寬
function fitLabelSize(label, maxW, base = 25, letterSpacing = 2) {
  const units = [...label].reduce((n, ch) => n + (/[\x00-\x7F]/.test(ch) ? 0.55 : 1), 0)
  return Math.min(base, Math.floor((maxW - letterSpacing * label.length) / units * 10) / 10)
}
```

資料列並排放不下就改成上下兩行（左標籤在上、數值在下）。
只要有一列放不下就整個面板都換行，避免同一塊面板混兩種排法。

狀態圓點：`ok` = 實心、`warn`/`err` = 空心。語意靠形狀不靠顏色。

引線：家電框邊 → 面板邊，兩端都用 `edgePoint()`（從 rect 中心朝目標射出、取與邊界的交點）算
——面板被拖到任意位置時，引線仍然會接在兩個框最靠近的邊上。

`foreignObject` 會裁切內容，所以框要比面板大 `PLATE_PAD * 2`、內層再 padding 推回去，
不然外陰影會被切掉。並加 `pointer-events: none` 避免蓋住底下的 SVG。

## 6. 桌面規格

投影在桌面上，觀眾在這裡放卡片。固定 1080p，所以不需要 clamp 的彈性——版面用純百分比。

### 6.1 九個感應區的排列

沿一個扁橢圓的**上半弧**排開；中樞坐在弧的基線上，
所以 NFC 01 ↔ 中樞 ↔ NFC 09 是一條水平線、圓頂朝正上方開。
**單數位（1-indexed 的 02/04/06/08）往內縮**，形成交錯的雙環扇形。

```js
ORBIT = { cx: 50, cy: 70, rx: 43, ry: 48, arcStart: 180, arcSweep: 180, inset: 0.7 }

function orbitPos(i, n = 9) {
  const f = n > 1 ? i / (n - 1) : 0.5
  const rad = (ORBIT.arcStart + f * ORBIT.arcSweep) * Math.PI / 180
  const k = i % 2 === 1 ? ORBIT.inset : 1
  return { x: ORBIT.cx + ORBIT.rx * k * Math.cos(rad),
           y: ORBIT.cy + ORBIT.ry * k * Math.sin(rad) }
}
```

### 6.2 版面參數

| 參數 | 值 | 說明 |
| --- | --- | --- |
| `panelPct` | 29.06 % | 不是隨手取的整數：1920×1080 下 `.app-body` 內容寬是 1858px，29.06% ＝ 540px，正好等於改成佔比之前 `clamp(420px, 32vw, 540px)` 的結果 |
| `slotSize` | 86 px | 感應圈直徑 |
| `hubSize` | 280 px | 中樞圈直徑。實際光環半徑 ＝ `hubSize/2 × 116/120`（`CenterHub` 的 SVG 是 viewBox 240 裡半徑 116） |
| `cards` | 1 / 1.55 / 1.35 | 三張卡的高度**權重**（相對值不是百分比） |
| `font` | 25 / 48 / 16 / 15 | title / stat / label / body，另有一個總縮放 `scale` 給投影距離用 |

> **凍結 — 單一讀取點**
> 版面幾何（左右佔比、圓圈大小、圓圈位置）**只有一個讀取點**：`config/tableTuning.js`。
> CSS 變數、連線 SVG 與 WebGL 發光層必須吃到同一組值——任何一處寫死就會錯開。
> App 把它掛成 `--panel-pct` / `--slot-size` / `--hub-size` / `--hub-x` / `--hub-y` 給 CSS 用。

字級的四個角色 ＋ 一個總縮放：其餘字級（單位、增減、座標軸、日期…）
都是從那四個用 CSS `calc()` 推導出來的。
字級與卡片佔比**互相牽動**（字調大 → 每張卡的 min-content 變高 → 佔比更容易失效），
兩組滑桿放在一起調就是這個原因。
`scale` 是投影距離用的總開關，不要用個別項去模擬總縮放。

### 6.3 slot 三態

| 狀態 | 圓環 | 文字 | 意義 |

| **離線** | `1px solid var(--glow-dim)` | `--c-text-dim` | 讀卡機沒連上 |
| **connected** | `border-color: rgba(160,216,255,0.34)` | `--c-text-mute` | 讀卡機在線、還沒放卡 |
| **active** | `border-color: var(--glow-rim)`<br>`background: rgba(160,216,255,0.07)`<br>`box-shadow: inset 0 0 12px rgba(160,216,255,0.14)` | `--c-text`<br>`letter-spacing: 0.18em` | 卡片在上面。**外圈光暈交給 WebGL**，這裡只留銳利的部分 |
| **focused** | 多一層 `--shadow-2` | — | 資訊面板正在顯示這一張。*不用顏色*，用陰影拉開層級 |

slot 內容：一個 `+` 號（17px, weight 300）＋ 兩位數編號（9.5px, letter-spacing 0.10em），
下方 7px 處是 `NFC 0X` 標籤（13px, letter-spacing 0.14em, uppercase）。

連線的端點都貼齊圓邊緣：`hubClear()` 與 `slotClear()` 跟著圓圈大小走，
寫死的話圓圈調大之後線會從圓圈裡面長出來。

SVG 那條 `.beam-halo` 在 active 時退到 `opacity: 0.25`
——在 bloom 的柔邊上再壓一條實心線會切出一道硬芯。
保留它是為了 WebGL 起不來時仍有連線可看。

中樞：一圈 hairline（viewBox 240、r=116、strokeWidth 1）＋ 下方 14px 的 `System Core` 標籤。
`color: var(--glow-dim)` → active 時 `var(--glow)`，SVG 走 `currentColor`。
舊版的同心環、72 根放射刻度、反向旋轉虛線弧、徑向漸層光核與 `feGaussianBlur` 全部移除了
——那些刻度不承載任何資訊，實際輸入只有 `activeCount > 0` 與 `wsStatus` 兩個位元。

### 6.5 InfoPanel：三張卡把高度分完

這一端是**投影，捲不動**——「往下還有東西」等於那些東西不存在。
所以三張卡不是「兩張固定 ＋ 趨勢圖吃掉剩下的」，而是三張一起把面板的高度分完：

```js
const share = (w) => ({ flexGrow: w, flexShrink: 1, flexBasis: 0 })
// 總和永遠剛好等於面板高度
```

| 卡 | 權重 | 內容 |
| --- | --- | --- |
| **今日 ＋ 本月** | 1 | 今日運轉 **2.6** hr ＋「較昨日 ↑10%」／ 分隔線 ／ 本月累積 68.4 / 目標 100 hr ＋ 進度條 68% |
| **趨勢** | 1.55 | y 軸六格刻度 ＋ 單位／24 根長條（日檢視），青→白漸層／x 軸 00 04 08 12 16 20 24 |
| **維養排程** | 1.35 | 表頭（項目 / 上次維養 / 下次維養 / 狀態）＋ 最多 4 列，每列帶線稿 icon。狀態「即將到期」＝反白 pill，「正常」＝次階文字 |

> **踩過的坑 — `flexShrink` 留 1，不要設 `minHeight: 0`**
> 設了之後卡片可以被壓到比內容還矮，而 `.device-dash` 是 `overflow: hidden`
> ——被裁掉的那幾列*不會有任何跡象*。
> 留 `min-height: auto` 的話，權重給太小的卡會停在自己的內容下限、剩下的由其他卡分；
> **佔比不準是看得出來的，無聲裁切不是。**
> 編輯面板會同時顯示「要求 %」與「實際 px」。

> **踩過的坑 — 「今日」與「本月」原本是兩張卡，合併不是為了好看**
> 維養排程是固定高度（最多 4 列約 232px）又排在最後，
> 面板一旦不夠高被犧牲的一定是它，而且是無聲切掉。
> 兩張卡各要 24px 內距 ＋ 22px 標題再加卡間 10px，合併省下約 100px ＝三列維養。
> 實測 1512×860 原本切掉 57px，合併後不再溢出。

> **踩過的坑 — 「日 / 週 / 月 / 年」那一排已經移除**
> 它是純 `<span>`、沒有任何點擊行為，而桌面是投影——觀眾切不了，擺著只會誤導，
> 而且要吃掉 38px 的高度（面板不能捲動，高度很珍貴）。
> 資料還留著（`trend` / `trendYMax` 有四個區間），要做成會動的切換再接回來。

「本月累積」降成「一行數字 ＋ 一條進度」的次階寫法：
今日的 48px 不能也給本月——兩個 48px 並排在 540px 的面板裡讀起來會分不出哪個是「現在」。
**階層靠字級，不靠卡片邊界。**

「較昨日」在**上**、百分比在下——DOM 順序就是視覺順序，不是靠 `column-reverse` 反過來。
反過來的話朗讀順序與選取順序會跟看到的相反。

### 6.6 面板換頁與輪播

```js

const FADE_MS   = 550    // 左滑出 → 右滑入
```

- 新刷的卡立刻奪焦並重新計時（每次新 tap 與每次輪播 tick 都會重啟計時器）。

三種檢視：`IdleView`（請將物件放上感應區 ＋ 系統狀態／資料來源）、

## 8. 2.0 實作計畫

依賴順序排的六個階段。每一階段有一個可驗證的關卡，過不了就不要往下走
——1.0 的每個坑都是在「先做畫面、後補架構」時踩到的。

### P0 — 骨架決策：monorepo ＋ 真套件

1.0 用「三個並排 repo ＋ 複製腳本」，理由是現場複製一個資料夾就能跑。
2.0 建議改成 pnpm workspace，並在 build 時把共用套件**打包進各端的 dist**
——同時拿到單一來源與「資料夾自帶完整程式碼」。

```
f-zone/
  packages/
    glow/         # shaders / ribbon / stage / scene / GlowLayer（現行 glow/）
    protocol/     # 訊息型別、DemoSocket、simKeys、useNfcSync（三端共用的記帳）
    tokens/       # SHARED 的唯一來源 → 產生 CSS 變數與 params
  apps/
    wall/  desk/  pad/
  server/         # ACR122U ↔ WS，維持獨立可單跑
```

- **新開 repo**，不要 fork——順便甩掉 F-table 歷史裡那顆 54.6 MB 的 `.ply`。
- `tokens` 產出兩份 artifact：CSS 變數區塊與 `params.js`（現行 `sync-tokens.mjs` 的邏輯照搬）。
- CI 掛 `--check` 模式，token 飄掉就讓 build 失敗。

**Gate**：三個 app 都能 `build`，且 `tokens --check` 在 CI 綠燈。

### P1 — 發光引擎：原封不動搬過去

把 `glow/` 五個檔案**逐字搬進 `packages/glow`**，不要「順便重寫」。
這五個檔案是三個月調參與量測的結果，每個常數背後都有一次實測。搬完再改介面。

- 先搬 `shaders.js` / `ribbon.js` / `stage.js` / `scene.js`，
  最後才是 `GlowLayer.jsx`（那是唯一綁 React 的一層）。
- 把 §3 的三個死規則（`col()`、`LinearSRGBColorSpace`、`DoubleSide`）
  寫成套件的 README 第一段。
- 牆面的 `webgl/FrameLines.js` 與 `webgl/TraceBeam.js` 是「綁死牆面幾何」的版本。
  2.0 可以評估讓牆面也改用通用版 `scene.js`，
  但要保留 `snap()` 偶數對齊與不透明 canvas（`uAlphaLuma = 0`）兩件事。

**Gate**：開一個 demo 頁畫一條斜線 ＋ 一個圓，跑彗星。
`?glowdbg` ＋ `readPixels` 量到的剖面與 1.0 相同。

### P2 — 協議層：一份型別、一份記帳

六種訊息定義成 TypeScript 型別（或 JSDoc ＋ 一支 runtime validator），
`DemoSocket` 與 server 都**從同一份型別產生**
——1.0 靠註解提醒「改 server 協議時這裡要一起改」，2.0 應該讓編譯器擋。

- 把三端各自寫的 `slot_index → id` 記帳抽成一個 `useNfcSync()`，回傳
  `{ activeIds, status, connectedReaders, sessionMode, startSession, endSession }`。
- session 控制維持「送出 → 等廣播回來 → 才切」，WS 斷線才走本地 fallback。
- `isDemo()` 的三條規則（`?live` > `?demo` > https 自動）逐字保留。
- 斷線時清空 `slotToId` 與 `activeIds`，避免卡在某個亮著的狀態；每 3 秒重試。

**Gate**：三端同時開著、server 帶 `--sim`，按 `a` 三個畫面在同一幀亮起；按 `0` 三個畫面同時熄。

### P3 — 牆面：先幾何、後光

牆面是三端中唯一「座標即物理」的一端，所以順序不能顛倒。

1. SVG 骨架 ＋ `viewBox 1920×1080` ＋ 十一個 `fill="#000"` 的框（照 §5.3 的座標表）。
2. 背景框架幾何（`FRAME` / `VLINES` / `HLINES`）＋ `snap()` 偶數對齊。
3. 接上發光層畫框架與框外圈，確認 idle 畫面正確（框架亮、十一個框全暗）。
4. `routing.js` 佈線 ＋ 走線光束。
   `?all` 檢查九條線不穿過電視預留區、不擦任何框邊。
5. 毛玻璃面板（照 §5.8 的排版公式與 §4.3 的兩層進場結構）。
6. 家電 WebP（照 §5.4 的產生方式）。
7. 編輯模式（鍵盤 `e`）。這不是 nice-to-have——現場對位靠它。

**Gate**：`?all` 下九個面板不重疊、九條走線不穿框；`?fps` 中位幀 ≤ 16.7ms。

### P4 — 桌面與 iPad：並行

兩端都吃同一組 `packages/glow` ＋ `packages/protocol`，可以兩個人平行做。

**桌面**

1. `tableTuning.js` 先寫好（它是四個消費者的唯一讀取點）。
2. 流動漸層背景——**先做這個**，因為 InfoPanel 的陰影決策依賴它（§4.2）。
3. 扇形 slot ＋ 中樞環 ＋ 發光層。
4. InfoPanel 三卡權重版面 ＋ 8 秒輪播 ＋ 550ms 左出右入。

**iPad**

1. `TOP.png` ＋ `aspect-ratio` ＋ mask 羽化，**z-index 0**。
2. 節點 / 中樞 / 卡片的 % 定位，三邊（CSS、leader SVG、發光層 `buildGlow`）用同一組數字。
3. 發光層：`ring-*` / `beam-*` / `edge-*` / `hub`，`minCorePx: 2.0`。
4. 毛玻璃卡片三件套（brightness/contrast ＋ 深色 tint ＋ 斜向高光）。
5. DetailCard ＋ 44px 觸控區 ＋ 完成浮層 ＋ 重置鈕。

**Gate**：兩端各自 `?demo` 跑完一輪自動編排沒有殘影、沒有一節一節的光暈。

### P5 — 現場化

- `reader-map.json`：把九台讀卡機名稱釘到畫面編號。
  **沒有這張表就是 USB 插入順序決定對應。**
- `uid-map.json`：補登記 `dehum` / `purifier` / `sensor` / `bathfan` 四張還沒有實體卡的。
- 六個逃生參數（§2.6）＋ kiosk 設定（`cursor: none`）＋ 啟動批次檔。
- 正式量牆後校正 `appliances.js` 的 x/y/w/h，然後開編輯模式**重對一次面板位置**
  （面板是絕對座標，不會自己跟著跑）。
- 三端各自 build 一份可獨立複製的 dist。

**Gate**：真硬體九台刷卡，三端同時反應；拔掉一台讀卡機那一格正確熄滅。

## 9. 驗收清單

全部可量測。「看起來對」不算過。

### 同步

- [ ] server 帶 `--sim`，按 `a`：三個畫面在同一幀亮起（錄影逐格確認）。
- [ ] 任一端送 `session-start`：三端的歡迎頁在同一時間開始 600ms 淡出。
- [ ] 拿走一張卡：三端只有那一台熄滅，其他八台不受影響。
- [ ] 拔掉一台讀卡機：對應那一格熄滅，且不會誤熄別台。
- [ ] WS 斷線：三端各自清空為待機，並每 3 秒重試。

### 視覺一致

- [ ] 三端同時全滿，截圖比對線的**顏色與光暈擴散**——同一支 shader 應該給出同一種光。
- [ ] `tokens --check` 綠燈（三份 CSS 的 `GLOW-TOKENS` 區塊沒有飄掉）。
- [ ] 底色三端都是 `#16181D`；牆面 canvas 的 clear color 與 CSS 同值
      （非 16:9 投影時 letterbox 邊界無色差接縫）。
- [ ] 牆面十一個框在 idle 時**完全不發光**，且框內是純黑（`readPixels` 量到 RGB 0,0,0）。

### 光暈品質

- [ ] iPad 全滿：沿每一條近水平的關聯邊掃描光暈亮度，**起伏 ≤ 0.25**

- [ ] 九台全滿：三端 `?fps` 中位幀 **≤ 16.7 ms**、p95 **≤ 18 ms**

## 10. 改進提案

每一項都附取捨。這些是「可以做」不是「應該做」——先問它服務不服務那一個互動動作。

| 提案 | 做法 | 代價 / 風險 |
| --- | --- | --- |
| **共用程式碼改真套件** | pnpm workspace ＋ build 時 bundle 進 dist。拿掉「改複製品會被蓋掉」這個長期陷阱，型別也能跨端檢查。 | 現場不再能「複製一個資料夾就跑」——要靠 build 產出。必須確認 dist 真的自帶全部程式碼。 |
| **協議上型別** | 六種訊息一份型別，server 與 `DemoSocket` 共用。1.0 靠註解提醒同步，2.0 讓編譯器擋。 | server 是 CommonJS，要一起搬。工作量不大但會動到現場已驗證的那支。 |
| **面板版面回到自動** | 1.0 的 `avoidX` 自動避讓還在（`panelBox()`），只是被 `PANEL_LAYOUT` 的絕對座標蓋掉。2.0 可以讓自動版面當預設、絕對座標只做例外覆寫。 | 自動避讓的結果沒有人工排版好看。折衷：正式量牆後先跑自動，只對不滿意的幾塊寫覆寫。 |
| **iPad 線粗併回 SHARED** | 現在 iPad 自己一組（0.009 / 0.011），改 SHARED 不連動。可以在 SHARED 加一組 `graphScale` 讓它變成推導值而非例外。 | 要重新調一次 iPad 的視覺。收益是「三端真的都吃同一份」，不是外觀改善。 |
| **編輯模式改成寫檔** | 現在覆寫值存 localStorage，調完要按「匯出」貼回程式碼。dev 時可以加一支 API 直接寫回 config 檔。 | 只在 dev server 下能用，正式 build 沒有這條路。要小心不要讓現場的 kiosk 意外寫檔。 |
| **資料接真 API** | 目前九台的數據全部是 mock。接 Welltek IoT Cloud 之後三端的資料層要換成「WS 事件 ＋ 輪詢 API」兩個來源。 | **展場網路不可靠。** 一定要保留 mock 作為 fallback，並且斷線時顯示的是最後已知值而不是空白或 0。 |
| **牆面統一用通用 scene.js** | 牆面現在有一組綁死幾何的 `webgl/`。改吃通用版可以把三端的繪圖路徑收成一條。 | 必須保留兩件牆面專屬的事：`snap()` 偶數對齊、不透明 canvas（`uAlphaLuma = 0`）。漏掉任何一件都會回到 §3 的兩個坑。 |
| **「日/週/月/年」做成會動的** | 桌面的資料已經有四個區間，只差一個能被觸發的切換。 | 桌面是**投影，觀眾摸不到**。要做就得由 iPad 送控制訊息過來——那會變成第二種互動，先問它值不值得。 |

## 11. 凍結項

2.0 可以重寫每一行程式碼。這幾件不行——改了現場就壞，**而且不會有錯誤訊息告訴你**。

### 01 · 九個家電 id

`hrv` · `ac` · `dehum` · `purifier` · `sensor` · `light` · `socket` · `curtain` · `bathfan`

橫跨三端 ＋ server 的 `uid-map.json` ＋ 已經貼在實體卡片上的 UID 對應。

### 02 · 牆面座標系

`viewBox="0 0 1920 1080"` ＋ `preserveAspectRatio="xMidYMid meet"`
＋ `.wall-stage { position: fixed; inset: 0 }` ＋ flex 置中。

加任何 padding / border / header 都會讓九個黑框整體位移，離開牆上的實體預留位。

### 03 · 十一個框是純黑

`fill="#000"`。投影機的黑 ＝ 不出光。
不要因為「純黑太重」而改成深灰，也不要在核心框裡放文字。

### 04 · 六種訊息的欄位形狀

特別是 `tag-remove` **只帶 `slot_index`**。每一端都必須自己記 `slot → id`。
`DemoSocket` 送出的訊息形狀與真 server 逐欄位相同，這一點也要守住。

### 05 · 三個 WebGL 死規則

`col()` 建顏色（不要 `new THREE.Color()`）、`outputColorSpace = LinearSRGBColorSpace`、
所有材質 `DoubleSide`。加上 `premultipliedAlpha: true` 與 `CustomBlending(One, One)`。

### 06 · 芯層 MAX、暈層加法

兩層不能用同一種混色。
芯層用加法會讓 32 個交叉點亮兩倍；暈層用 MAX 會把光暈砍成一條硬邊帶。

### 07 · 玻璃底板不進會動 opacity 的群組

`opacity < 1` 的祖先會建立新的 backdrop root，`backdrop-filter` 就取樣不到背景。
玻璃在外層永遠 opacity 1，文字與引線在內層淡入淡出。

### 08 · 只有三種循環動畫

走線彗星、底光呼吸、進出場淡入淡出。**彗星不呼吸。**
1.0 移除過旋轉刻度、掃描弧、放射線、同心環——不要再加回來。

### 09 ·「已套用編輯值」提示

三端的編輯模式覆寫值存在 localStorage。
**面板關著但有覆寫值時角落一定要顯示提示**
——那是唯一會讓人發現「現在畫面不是程式碼裡那一版」的線索。

### 10 · 節奏

0.28s 進出場、600ms 歡迎頁淡出（三端綁定）、8s 面板輪播、1.5s / 3.0s 呼吸。
這幾個數字是為年長觀眾調的，不要「順手」加快。
